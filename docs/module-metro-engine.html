metro-engine

Metronome audio engine, 2.10 spike: checks that a metronome keeps playing with the phone screen locked. Browser glue (Web Audio, media elements, Media Session); the timing math lives in metro-clock.

Why a pre-rendered loop

Android throttles JavaScript timers in the background, so a setTimeout lookahead scheduler stalls once the screen is locked. Here one cycle (one bar, 4 beats in the spike) is rendered once with an OfflineAudioContext into an AudioBuffer, then played by an AudioBufferSourceNode with loop = true: no JavaScript runs while it plays.

A tempo change renders a new cycle and swaps it in right away, even mid-beat (swapPoint): the old source stops and the new one starts at the same audio time.

Tempo goes down to 1 BPM: one 4/4 bar then lasts 4 minutes, a 46 MB buffer (23 MB as WAV). Fine for the spike; V1 may render one beat at very slow tempos.

Three outputs (to be measured on a phone)

  • direct: source → AudioContext.destination.
  • stream: source → MediaStreamAudioDestinationNode, whose stream is played by an <audio> element. Chrome may only show lock-screen media controls (Media Session) for media elements.
  • wav: the cycle is encoded as a WAV file (repeated to last about 10 s) and played by an <audio loop> element. No Web Audio at play time, but a tempo change is not sample-accurate (the phase is kept, not the beat).

The shared audio context comes from audio.
