storage

Persistance du carnet (notes et dossiers), et sauvegarde/restauration en fichier JSON.

Où sont les données ? (depuis la 2.1)

Dans IndexedDB (voir db) : un enregistrement par note et par dossier. Jusqu'à la 2.0, tout le carnet était une seule chaîne JSON dans localStorage, ce qui posait deux limites :

  • taille : environ 5 Mo par site pour localStorage, contre des centaines de Mo pour IndexedDB ;
  • coût : chaque frappe réécrivait le carnet entier. Désormais, seule la note modifiée est écrite.

Les métadonnées (affichage choisi, dossier sélectionné, date de dernière sauvegarde…) restent dans localStorage : elles sont minuscules, et les lire de façon synchrone est pratique.

Migration depuis localStorage

Au premier lancement de la 2.1, loadAll copie les notes et dossiers de localStorage vers IndexedDB, en une seule transaction (tout ou rien), puis note storage: 'idb' dans les métadonnées. La copie n'a lieu que si la base IndexedDB est vide : des données déjà présentes ne sont jamais écrasées par l'ancienne copie.

L'ancienne copie n'est pas effacée : elle reste en filet de sécurité (figée à la date de la migration). Règle d'or : ne jamais déplacer et supprimer des données dans la même opération.

Si IndexedDB est indisponible (navigateur très ancien, stockage bloqué), l'app continue avec localStorage, comme avant la 2.1.

Stratégie d'écriture

  • Debounce : chaque modification programme une écriture 150 ms plus tard ; les frappes rapprochées n'en déclenchent qu'une.
  • Notes « sales » : scheduleSave reçoit l'id de la note modifiée ; seules ces notes sont écrites.
  • Comparaison : flushSave compare chaque note à sa dernière version écrite (sa forme JSON) et n'écrit que les différences, suppressions comprises. C'est un filet de sécurité : après une opération groupée (import, suppression d'un dossier…), rien ne peut être oublié, même si l'appelant ne sait pas quelles notes ont changé.
  • Flush sur visibilitychange (voir main) : Android peut tuer une app en arrière-plan sans prévenir ; on écrit donc tout de suite, en mode strict (le navigateur attend que ce soit sur le disque).
  • navigator.storage.persist() demande au navigateur de ne pas évincer les données quand l'espace disque manque.

Les écritures sont asynchrones et leurs erreurs (quota dépassé…) ne bloquent pas l'app : une note non écrite reste « différente » et sera retentée à l'écriture suivante.

(static) importFile(notes, text, foldersopt) → {ImportResult}

Description:

  • Importe un fichier dans le carnet : note partagée (.inkline) ou sauvegarde complète.

    • Note partagée : elle est ajoutée avec de nouveaux identifiants, sans jamais écraser une note existante (recevoir deux fois la même note en crée deux copies, c'est voulu : on ne sait pas laquelle garder).
    • Sauvegarde : fusion par id, la version la plus récente (updated) gagne. Importer deux fois la même sauvegarde est sans effet. Les dossiers d'une sauvegarde v2 absents du carnet sont ajoutés ; ceux qui existent déjà (même id) sont conservés tels quels. Une sauvegarde v1 (sans dossiers) reste lisible.

    Dans les deux cas, tout passe par sanitize.
